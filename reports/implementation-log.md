## Item 10: stratified hand-check sample (B9, part)

* **Generated (seed 20261016, strata = approval lanes, denominator 4,868 candidates):** `data/upstream-import/classified/handcheck-sheet.csv` (300 rows, canonical keys and pipeline attributes only, no handles; blank `verdict`, `is_mcp_server_or_client`, `identity_correct`, `duplicates_correct`, `notes`) and `handcheck-sample-summary.json`. Population / drawn: bulk 1,216 / 106; individual 1,949 / 89; needs_review 1,353 / 63; family_sample 302 / 21; blocked 35 / 11; not_eligible 13 / 10.
* **Decision rule implemented (C4):** a stratum FAILS only if the lower 95% Wilson bound of its incorrect-or-unclear share exceeds 5%; PASS only if the upper bound is at most 5%; otherwise INCONCLUSIVE; unchecked = NOT CHECKED.
* **Statistical limit to plan around:** showing "under 5%" needs about 73 clean checks in a stratum (0 incorrect of n gives an upper bound of roughly 3.84 / (n + 3.84)). The 106 in the bulk lane suffice if almost all are clean; the 21 in family_sample and 10–11 in the small strata can only come out INCONCLUSIVE or FAIL, so those lanes must be reviewed individually or the sample enlarged before any bulk approval relies on it.
* **Verified (run here):** `npm test` 102 pass, 0 fail. No reviewer verdicts exist yet; nothing about precision is claimed.

## Item 11: removal hold fails closed in the loader (review finding)
* **Finding (automated background review of the pushed commits, details not provided; assessed on the code):** `load.mjs` derived `candidate.removal_hold` only from the classifier field `quality_indicators ∋ removal_request_pending`. A removal request that the loader itself resolved to a candidate did not hold it, and the reconcile check compared against the same field, so a classifier gap would have passed unnoticed (fail-open).
* **Fixed:** after dispositions are written, every candidate that is the target of a `removal_request` disposition gets `removal_hold = true` (raise-only; a reload never clears a hold; clearing remains the individual reviewer function `clear_removal_hold`). Reconciliation now has an independent check (a removal target without a hold) and "classifier-held candidates without a database hold = 0" in place of an exact-equality check, since the database may hold more than the classifier.
* **Tests added (3):** hold added when the classifier output has none; reconcile flags a removal target without a hold; a reload keeps a hold set elsewhere.
* **Verified (run here):** `npm run test:db` 16 loader tests + both SQL suites pass; full snapshot reload: 0 holds added (the classifier already covered all resolved removal targets), reconciliation OK, second load inserts nothing.
* **Residual gap:** removal requests whose target cannot be resolved to exactly one candidate key have no hold from the loader (only the classifier's weak-match and removal-like-comment holds apply); those need the manual removal-request workflow (C3).

## Item 12: interim review workflow (C2) and a gate bug it exposed
* **Added:** `tools/upstream-import/review.mjs` (`reviewQueue` in the C3 order: ambiguous group, security flag, removal hold, needs_review, individual lane, family sample, bulk lane; `writeSheet`; `validateDecisions`; `applyDecisions` with one savepoint per decision, as a named reviewer, optional dry run), `lib/csv.mjs` (shared CSV reader), `db/tests/review.test.mjs` (10 tests). Allowed actions: approve, reject, reopen, mark_unavailable, unpublish, clear_security_flag, clear_removal_hold, suppress. **`publish` and any bulk action are not accepted** (C6: nothing is published before the Phase D gates). Every decision needs a reason and goes through `review_candidate` / `clear_*` / `suppress_candidate`, so gates, guards, `review_decision` and `audit_log` apply. The loader now stores `lane`, `evidence_level` and `ambiguity_flags` in the evaluation evidence so the queue can be built from the database alone.
* **Defect found in `0002_publication_boundary.sql` and fixed:** `publication_gate_failures` built its result with `f := f || 'P3 removal hold'`, which Postgres parses as appending an *array literal*, so every failing gate raised `malformed array literal: "P3 removal hold"` instead of returning the gate list. Approvals and listings were still blocked, but only by that accidental error and with unusable messages. All ten appends now use `array_append(f, '…'::text)`.
* **Why the earlier SQL suite missed it, and the hardening:** `_expect_error` matched a loose needle ('P2', 'P3') that also appeared inside the malformed-literal message. The helper now fails on internal-error signatures (malformed, syntax error, does not exist, invalid input syntax, cannot be cast, operator/function does not …) before comparing, and the review test asserts the real message (`approval blocked by gates … P3 removal hold`).
* **Verified (run here):** `npm run test:db`: both SQL suites pass and 26 Node tests pass (16 loader + 10 review).
* **Lesson recorded:** negative tests must assert the specific expected failure, not a substring that an unrelated error can contain.
